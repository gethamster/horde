# Advisory Jev work-product review

Horde can ask Jev to inspect work products at durable workflow checkpoints. The result is advice for an operator or a later reviewer. It never changes a step result, chooses a worker, approves delivery, or merges a pull request. A Jev result alone is not an independent generative review.

Add `review_enabled = true` to the operator-owned `[decision]` section in `~/.config/horde/config.toml` while `mode = "shadow"`. The setting defaults to false and cannot be enabled by a repository file. The same `TYPESAFE_API_KEY` credential used for shadow routing can live in `~/.config/horde/credentials.env` (owner-readable only). New tasks pin the operator settings. The daemon rechecks the current operator settings and credential before preparing a review and before every provider attempt.

The scanner creates one durable checkpoint per relevant event: task submission or plan revision, completed agent patch, successful integration, integration conflict or failed validation, failed step, command or environment verification, delivery step, and final task status. Each checkpoint creates a separate `review:<kind>` decision row using the `review-v1` question catalog. Six risk questions and one specialist recommendation share a single TypeSafe request. The bounded review queue has two provider slots and 32 waiting jobs; task decision limits also apply. Overflow, interruption, configuration drift, and incomplete evidence remain inspectable.

For code checkpoints, Horde records the base and integrated commit, all changed paths with status, rename source and binary marker, and bounded diff excerpts. Each path states whether its content was covered. Binary paths, excerpts omitted beyond the eight-path limit, and truncated or unavailable excerpts make coverage incomplete; Horde abstains rather than implying Jev reviewed unseen content. It also abstains when the workspace is missing or dirty, the event-time head, revision, or context version changed, the manifest cannot be collected, or the request exceeds Jev's limit. A redacted evidence artifact binds the revision, inherited context version, external-operation digest, and observed generative-review attempts. `horde reviews TASK_ID` and the MCP `reviews` operation return coverage and a `fresh` flag. Freshness requires complete coverage and an unchanged revision, context, integrated head, clean worktree, and external-operation state. Use the returned event sequence as the `--after` cursor.

Reviews run asynchronously after the checkpoint event. A dependent generative reviewer can start before Jev finishes; this version does not claim that Jev advice reached that reviewer. The recorded reviewer attempts are provenance, not an attestation of independent review of the same commit. After a restart, Horde safely requeues checkpoints that never left the durable queue. A review that began preparation remains interrupted for inspection even if its provider attempt counter is zero, because an uncertain request could have crossed the network. The scan cursor starts at the newest event when the migration is installed, so enabling review does not retroactively send old work products to the provider.
