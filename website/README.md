# horde.sh

A minimal Next.js 16.3 landing page with a copyable install command, an
explanation of what Horde is and when to use it, and guides at `/docs`,
`/docs/agents`, `/docs/configuration`, and `/docs/deployment`, plus `/about`,
`/contact`, and `/privacy`. Copy success appears as a checkmark, with
confirmation text available to screen readers.

With Node.js 22 or newer:

```sh
npm ci
npm run dev
```

`npm run check` checks TypeScript. `npm run build` verifies the public key,
renders `public/og.png`, produces the static site in `out/`, and then generates
the agent-facing files described below. `npm test` runs the suite in `test/`
against `out/`, so build before testing. Release CI renders the installer from
`scripts/install-template.sh`; website builds do not generate or publish it.

Source is maintained at [gethamster/horde](https://github.com/gethamster/horde).
The Vercel project `horde` uses that repository’s `main` branch and the `website`
Root Directory. Signed downloads continue to come from `asomervell/horde-releases`.

## The agent-facing surface

These are descriptions of Horde, not a service. Horde runs on the user's own
machine and is driven over MCP or the CLI; the site publishes no API of its own,
and nothing here should be described as one.

`scripts/pages.mjs` is the single source of truth for indexable pages and for
retired paths that still need to redirect. Adding a page there and creating its
route is enough: the sitemap, `llms.txt`, the
Markdown variants, and the routing in both `vercel.json` files are all derived
from it, and `npm test` fails if any of them fall behind.

`npm run build` emits, into `out/`:

- `llms.txt` and `llms-full.txt` — what Horde is, when an agent should reach for
  it, and links to everything below.
- `sitemap.xml` and `robots.txt` — every indexable URL, with `lastmod` taken
  from the last commit that touched each page.
- `.well-known/mcp.json` — Horde discovery metadata: transport, install, platforms,
  version, operation counts, and contact. Its `format: "horde-discovery"` and
  `formatVersion: 1` identify a Horde-specific format, not an official MCP schema.
  The installed server uses stdio; this URL is not an HTTP MCP endpoint.
- A Markdown variant of every page, converted from the rendered HTML so the two
  cannot drift, plus a short `404.md` recovery map and RFC 9457 `404.json`.

`public/.well-known/tools.json` is different: it is generated from the Rust source by
`UPDATE_WEBSITE_SPEC=1 cargo test --test website_spec` and committed. The same
test fails when the daemon's tool surface changes without regenerating it, so
regenerate and commit it whenever `src/protocol.rs` gains or loses an operation.

Both `vercel.json` files are generated by `node scripts/generate-vercel-config.mjs`
and committed, because Vercel reads them before the build runs. Edit the
generator, never the JSON.

The generator uses Vercel’s routing compiler to retain existing headers,
redirects, and clean URLs, then adds explicit page destinations, a filesystem
check, and terminal error routes. Low-level `routes` are required because a
high-level rewrite to `404.md` would return 200. Do not combine `routes` with
`headers`, `redirects`, `rewrites`, or `cleanUrls` in the generated config.

Existing pages still redirect `Accept: text/markdown` to their `.md` variant.
Missing paths return a real 404: JSON requests receive RFC 9457 Problem Details
(`application/problem+json`) with a code, explanation, hint, and recovery links;
Markdown requests and generic crawlers receive short Markdown; browsers receive
the existing HTML page. Error responses vary on Accept and carry `noindex`.
`/openapi.json` now returns 404 instead of redirecting to an unrelated format.
There is no hosted API to describe. Existing retired documentation and catalog
redirects remain supported.

`test/serving.test.mjs` exercises the compiled route table over HTTP, including
all public pages, Markdown variants, discovery files, clean URLs, and missing
paths. Vercel’s local emulator ignores `has` conditions, so it cannot validate
Accept negotiation. After deploying, repeat the checks against the canonical
host, including:

```sh
curl -sS -D - https://www.horde.sh/a-path-that-does-not-exist
curl -sS -D - -H 'Accept: text/markdown' https://www.horde.sh/a-path-that-does-not-exist
curl -sS -D - -H 'Accept: application/json' https://www.horde.sh/a-path-that-does-not-exist
curl -sS -D - -H 'Accept: text/html' https://www.horde.sh/a-path-that-does-not-exist
curl -sS -D - https://www.horde.sh/openapi.json
```

All five must return 404. Inspect the response media type and recovery links as
well as the status. Check existing pages and install/release redirects too.

Search indexing still requires the site owner to verify Search Console/Bing
Webmaster Tools and submit the sitemap. Keep the canonical host aligned with the
Vercel primary domain (currently `www.horde.sh`, one hop from the apex). The public business address in `app/site.ts` supplies both the contact page and
Organization PostalAddress. Publishing the existing CLI through Homebrew/npm/PyPI requires choosing a
registry, establishing ownership, and configuring release credentials; signed
GitHub releases remain the supported installation channel.

Vercel can use either the repository root or `website` as its Root Directory:
each has a `vercel.json` with explicit install, build, and output paths. These
configs serve the export as static files. No environment variables or server
process are required. Assign `horde.sh` to the Vercel project and serve it over
HTTPS so the copy button can use the Clipboard API.

The export hosts `/release-key.pem` and `/release-key.hex`. Vercel redirects
`/install` to the latest published release’s `install.sh`, and redirects `/releases/latest/<file>` and
`/releases/v<version>/<file>` to public GitHub Release assets in `asomervell/horde-releases`. These redirects require a
published release. Website deployments have their own lifecycle: edits to pages
and docs can ship while a binary release is building. The installer changes only
when a new release is published.

Only the public verification key belongs here. The private key belongs in the
GitHub `release` environment's signing secret. See
[release instructions](../docs/installing.md) for signing and publication.
